# PlayStead 0.4.3 — Provider Game Metadata Foundation

## Status

Proposed design for Task 12. Home UI and suggestion selection remain out of scope.

## Intent

Introduce a provider-neutral snapshot of authoritative game/store metadata. The
first provider is Steam's existing local `appinfo.vdf` source. This metadata is
separate from provider activity metadata, which continues to own playtime and
last-played values.

The layer prepares later consumers such as Suggestion du moment, Game Detail,
Library filtering and search without introducing recommendation logic in this
task.

## Non-goals

- No Home UI change.
- No Suggestion du moment selection.
- No provider activity or session schema change.
- No community-tag scraping, rendered-page scraping or AppId-specific constants.
- No polling or blocking startup dependency on provider availability.

## Domain contract

`ProviderGameMetadata` is an immutable provider-neutral snapshot keyed by
`GameId` and provider identity (`ProviderKind`, external id). It contains:

- official `Genres`;
- raw/normalized provider `Categories` or features;
- nullable `ReleaseDate`;
- nullable developer and publisher collections;
- nullable `IsFree`;
- nullable capability flags for single-player, multiplayer, online co-op and
  local co-op;
- `RefreshedAtUtc` and an availability/completeness state.

Unknown values remain unknown. Collections are normalized, de-duplicated and
stored deterministically. `SupportsCoop` is a nullable derived property:

- `true` when either `SupportsOnlineCoop` or `SupportsLocalCoop` is `true`;
- `false` when both are explicitly `false`;
- `null` for every other combination.

Thus `(true, null)` and `(null, true)` produce `true`, `(false, false)` produces
`false`, and `(null, null)`, `(false, null)` and `(null, false)` produce `null`.
Future weekend Suggestion du moment selection will require
`SupportsCoop == true`; unknown is never treated as false. `SupportsCoop` is
never persisted as an opaque replacement for the two authoritative flags.

## Provider-neutral boundaries

Core exposes:

- `IProviderGameMetadataSource`, returning snapshots for present installations;
- `IProviderGameMetadataStore`, loading and upserting snapshots;
- `ProviderGameMetadataReconciliationService`, which compares snapshots,
  preserves unchanged values, emits one `Changed` event only when a snapshot
  changes, and swallows ordinary provider failures after retaining the last
  known data. Cancellation remains cancellable and is not converted into a
  successful refresh.

Consumers depend only on these contracts and never on Steam-specific events or
types.

### Field presence for partial refreshes

Nullable values alone cannot distinguish an omitted provider field from an
explicit provider statement that the field is unavailable. Source results
therefore carry a per-field `ProviderField<T>` state with exactly three cases:

- `NotReported`: the provider did not include the field in this refresh;
- `Value(T)`: the provider reported a concrete value, including an explicitly
  empty collection where that is meaningful;
- `ExplicitUnknown`: the provider reported that the field is unavailable or
  unknown.

The reconciliation merge is uniform for release date, developers, publishers,
`IsFree`, all capability flags and other nullable metadata:

- `NotReported` preserves the persisted value;
- `Value(T)` replaces the persisted value;
- `ExplicitUnknown` persists a null/unknown value.

Collections use the same presence contract: an absent collection is
`NotReported` and preserves the existing collection; an explicitly empty
collection is `Value(empty)` and clears it; an unavailable collection is
`ExplicitUnknown`. The source presence state is retained through reconciliation
so these cases cannot be collapsed accidentally.

## Steam source

The existing Steam local integration remains the source of truth. The metadata
source reuses the current Steam root/library-folder discovery, installation
identity and `SteamAppInfoReader` access to `appcache/appinfo.vdf`.

The reader will expose the fields needed by the new source while retaining its
existing developer/publisher behavior. Mapping is explicit and covered by tests:
Steam's canonical single-player, multiplayer, online-co-op and local/shared-
screen-co-op category values map to the corresponding nullable capability flags.
Unrecognized or absent categories do not become `false`.

The mapping table will be centralized and tested against the exact category
identifiers/descriptions emitted by the local `appinfo.vdf` fixtures:

| Steam category | Neutral field |
| --- | --- |
| Single-player | `SupportsSinglePlayer = true` |
| Multi-player | `SupportsMultiplayer = true` |
| Online Co-op | `SupportsOnlineCoop = true` |
| Local Co-op / Shared-Screen Co-op | `SupportsLocalCoop = true` |

The implementation will record the exact numeric identifiers found in the
authoritative fixtures in the mapping tests; no unverified identifier will be
guessed or treated as a capability.

Genres are stored separately from categories/features. Release dates are parsed
only when Steam provides a reliable normalized value; missing or unparseable
dates remain `null`.

## Persistence

Add a dedicated SQLite table through migration `013_provider_game_metadata.sql`.
The migration is additive and backward-compatible. The table has one current
snapshot per `(game_id, provider)`, stores the provider external id, normalized
collections, nullable fields, refreshed timestamp and availability state. It does
not alter `provider_activity_metadata`, sessions or library tables.

`RefreshedAtUtc` means the timestamp of the last successful provider refresh.
The store compares semantic metadata independently from freshness:

- **Semantic change:** persist the merged metadata and new `RefreshedAtUtc`, then
  emit one canonical `Changed` event.
- **Freshness-only change:** metadata is semantically identical, so update only
  `RefreshedAtUtc` and emit no `Changed` event.
- **Provider failure:** preserve the last metadata and freshness timestamp; do
  not fabricate a successful refresh and do not emit `Changed`.

Both semantic and freshness-only successful refreshes are persisted atomically.
When a source reports a partial snapshot, the field-presence contract above
prevents unavailable fields from overwriting known values. Explicit provider
transitions to unknown are persisted only when reported as `ExplicitUnknown`.

## Startup and explicit refresh

Register the metadata store, Steam source and reconciliation service in the
existing host composition. The existing startup/refresh orchestration invokes
metadata reconciliation after the library snapshot is available, without making
provider access a prerequisite for rendering the application. Explicit provider
or library refreshes reuse the same service; no timer or polling loop is added.

Provider failures leave the previous snapshot intact and are observable only via
existing diagnostics/logging. Startup remains usable offline.

## Verification contract

Focused tests will prove:

- Steam genre/category mappings, including online and local co-op;
- `SupportsCoop` tri-state derivation and unknown preservation;
- release date, developer and publisher persistence;
- absent fields do not become fabricated defaults;
- `NotReported` preserves known scalar/capability values;
- `ExplicitUnknown` clears known scalar/capability values;
- absent collections preserve existing collections;
- explicit empty collections clear existing collections;
- unchanged snapshots do not write or notify;
- changed snapshots persist and notify;
- freshness-only refreshes update `RefreshedAtUtc` without emitting `Changed`;
- failed refreshes preserve the previous snapshot and do not block startup;
- application-facing contracts remain provider-neutral;
- provider activity metadata remains separate and unchanged.

The task will run provider metadata, Steam mapping, Data migration/store,
bootstrap tests as applicable, a Release warnings-as-errors build and
`git diff --check`. No WPF runtime launch is required.

## Acceptance boundaries

The task is complete when the provider-neutral model, Steam source mapping,
dedicated additive persistence, reconciliation notifications and offline
preservation are covered by focused tests. No Home or Suggestion du moment
behavior is changed until a later task consumes these snapshots.
