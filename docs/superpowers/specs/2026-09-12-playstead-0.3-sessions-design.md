# PlayStead 0.3 — Sessions Design

**Date :** 2026-09-12
**Version cible :** `0.3.0-dev`
**Branche cible :** `feat/0.3-sessions`
**Baseline :** `61996c2430511f072b9489e03c83d4b7253d769c` (`feat/0.2-steam-reference`)

---

## 1. Objectif

PlayStead 0.3 ajoute un moteur de suivi local des sessions de jeu fondé sur les processus Windows réellement observés.

La version 0.3 doit :

- détecter le démarrage et la fin réels d'une session de jeu ;
- suivre plusieurs jeux simultanément ;
- persister fréquemment l'état des sessions actives ;
- récupérer proprement une session après crash de PlayStead ou redémarrage Windows ;
- permettre des corrections manuelles traçables ;
- séparer strictement le temps observé localement du temps de jeu fourni par un provider ;
- fonctionner même si le jeu est lancé hors de Steam ;
- continuer à suivre les sessions lorsque la fenêtre PlayStead est fermée mais que l'application reste active dans le systray ;
- fournir une vraie page **Sessions** déjà structurée et réutilisable, sans attendre la refonte visuelle globale de 0.4.

La version 0.3 ne doit pas devenir un module d'analytics avancé. Les graphiques, tendances, calendriers, objectifs et visualisations statistiques restent hors scope.

---

## 2. Principes non négociables

### 2.1 Le processus réel est la source de vérité

Une session PlayStead correspond à un jeu réellement observé en cours d'exécution.

PlayStead ne considère pas qu'une session existe simplement parce que :

- Steam indique que le jeu est lancé ;
- un launcher est ouvert ;
- un anti-cheat autonome est actif ;
- un serveur dédié tourne ;
- un crash reporter existe ;
- un outil situé dans le dossier du jeu est ouvert.

La présence d'au moins un **processus principal reconnu** est nécessaire pour ouvrir ou maintenir une session.

### 2.2 Aucune session passée inventée

Si PlayStead était complètement arrêté pendant qu'un jeu tournait, PlayStead ne reconstruit pas artificiellement une session historique complète à partir d'une information externe.

Au redémarrage, PlayStead travaille uniquement à partir de ses propres preuves persistées et du dernier timestamp fiable qu'il a réellement observé.

### 2.3 Temps provider et temps observé restent distincts

Le temps de jeu fourni par Steam ou un autre provider est une donnée externe.

Le temps PlayStead correspond uniquement aux sessions observées localement.

Ces valeurs ne sont jamais fusionnées dans un compteur unique au niveau du modèle de données.

### 2.4 Corrections manuelles traçables

Une correction manuelle ne réécrit jamais silencieusement l'observation d'origine.

PlayStead conserve :

- les timestamps observés ;
- la valeur corrigée ;
- le fait qu'une correction manuelle a eu lieu ;
- la date de correction.

## 4. Architecture générale

Le moteur Sessions reste dans le processus WPF principal de PlayStead et utilise le **Generic Host** déjà présent.

Nouveaux blocs logiques :

```text
PlayStead.Core
  Sessions/
    Session
    SessionState
    SessionEndReason
    ProcessSignature
    SessionCorrection
    Session transition policies

PlayStead.Data
  Sessions/
    SQLite persistence
    migrations
    stores

PlayStead.Platform
  Processes/
    Windows process snapshot source

PlayStead.UI
  Sessions/
    SessionMonitor
    SessionRuntime
    SessionViewModel
    Session detail/history UI
  Tray/
    Tray lifecycle
```

Aucun nouveau processus, service Windows ou daemon n'est introduit.

## 5. Signatures de processus

Chaque jeu peut posséder une signature persistée.

Une signature contient :

```text
GameId
MainExecutables[]
AuxiliaryExecutables[]
ExcludedExecutables[]
UpdatedAtUtc
DetectionOrigin
```

### 5.1 Processus principaux

Un ou plusieurs noms d'exécutables peuvent être déclarés principaux.

Exemple :

```text
Game.exe
Game-Win64-Shipping.exe
```

Une session démarre lorsqu'au moins un processus principal associé au jeu est observé.

La session reste active tant qu'au moins un processus principal reconnu est vivant.

### 5.2 Processus auxiliaires

Les auxiliaires fournissent du contexte mais ne peuvent jamais ouvrir seuls une session.

Exemples :

- launcher restant ouvert pendant le jeu ;
- processus enfant spécifique au jeu ;
- runtime compagnon nécessaire.

Ils pourront aider à diagnostiquer une signature, mais la règle 0.3 reste :

> aucun processus principal = aucune session active.

### 5.3 Exclusions

Les exclusions empêchent explicitement certains exécutables d'être interprétés comme processus principaux ou auxiliaires pertinents.

Exemples :

- `CrashReportClient.exe`
- serveur dédié ;
- benchmark ;
- éditeur/modding tool ;
- updater ;
- anti-cheat autonome ;
- launcher ne représentant pas le jeu lui-même.

### 5.4 Origine d'une signature

Une signature peut être :

- `Discovered` — générée à partir d'une observation contrôlée ;
- `Manual` — corrigée ou créée explicitement ;
- `BuiltIn` — réservée à de futures signatures livrées par PlayStead.

0.3 ne requiert pas de base communautaire ou distante de signatures.

---

## 6. Découverte initiale d'une signature

0.3 ne doit pas appliquer une heuristique aveugle du type « tout `.exe` sous le dossier d'installation ».

La découverte automatique doit rester conservatrice.

Approche recommandée :

1. PlayStead connaît le dossier d'installation du jeu.
2. Lorsqu'un processus Windows apparaît, PlayStead vérifie son chemin exécutable.
3. Si ce chemin est situé dans ou sous le dossier d'installation du jeu, le processus devient un **candidat**.
4. Les exclusions évidentes connues par convention peuvent être filtrées.
5. Une signature candidate n'est promue comme processus principal que lorsqu'elle passe les règles de cohérence définies par le moteur.
6. L'utilisateur peut corriger la signature depuis l'UI si nécessaire.

Une mauvaise détection ne doit pas produire silencieusement des heures de jeu fausses.

## 7. Modèle de session

Une session observée contient au minimum :

```text
SessionId
GameId
ObservedStartedAtUtc
LastSeenAtUtc
ObservedEndedAtUtc?
State
EndReason?
DetectionSource
CreatedAtUtc
UpdatedAtUtc
```

### `SessionState`

```text
Active
Ended
Recovered
```

`Recovered` représente une session qui a dû être clôturée au redémarrage à partir du dernier timestamp fiable.

### `SessionEndReason`

Minimum 0.3 :

```text
ProcessExited
RecoveredAfterUnexpectedShutdown
ManualStop
Corrected
```

`Corrected` n'est pas utilisé pour masquer la raison observée d'origine ; il indique qu'une correction affecte la session.

---

## 8. Correction manuelle

Les corrections doivent être stockées séparément de la session observée.

`SessionCorrection` contient au minimum :

```text
CorrectionId
SessionId
CorrectedStartedAtUtc?
CorrectedEndedAtUtc?
Reason?
CreatedAtUtc
```

La durée effective affichée est calculée avec les valeurs corrigées lorsqu'elles existent.

La session conserve toujours les timestamps observés initiaux.

0.3 ne nécessite pas de versioning multi-corrections complexe. Une correction active par session suffit ; sa modification remplace la correction précédente tout en conservant les données observées.

---

## 9. Monitoring Windows

### 9.1 Source de snapshots

`PlayStead.Platform` expose une abstraction de lecture des processus Windows.

Le moteur ne dépend pas directement de `System.Diagnostics.Process`.

Contrat conceptuel :

```csharp
public interface IProcessSnapshotSource
{
    Task<IReadOnlyList<ProcessSnapshot>> GetProcessesAsync(
        CancellationToken cancellationToken);
}
```

`ProcessSnapshot` fournit au minimum :

```text
ProcessId
ExecutableName
ExecutablePath
StartedAtUtc?
```

L'impossibilité de lire le chemin d'un processus protégé ne doit jamais faire planter le cycle complet.

### 9.2 Polling

0.3 utilise un polling simple et robuste.

Intervalle cible :

```text
2 secondes
```

Ce choix évite d'introduire immédiatement une architecture ETW/WMI event-driven plus complexe.

Le polling peut être rendu configurable en interne pour les tests, mais aucune option utilisateur n'est requise en 0.3.

### 9.3 Plusieurs sessions simultanées

Le moteur doit pouvoir maintenir plusieurs sessions actives lorsque plusieurs jeux reconnus sont réellement ouverts.

Aucune hypothèse « un seul jeu à la fois » n'est autorisée dans le domaine ou la persistance.

---

## 10. Persistence active et recovery

Une session active doit être persistée fréquemment.

Chaque cycle de monitoring qui confirme la présence du jeu met à jour le `LastSeenAtUtc` si nécessaire.

Pour limiter les écritures SQLite inutiles, le moteur peut appliquer une granularité de persistance interne.

Cible recommandée :

```text
heartbeat persistant toutes les 5 secondes
```

Le polling reste à 2 s ; toutes les observations n'imposent donc pas une écriture DB.

### 10.1 Redémarrage normal

Lors d'une fermeture propre de PlayStead alors qu'un jeu tourne, PlayStead ne doit pas inventer que le jeu s'est arrêté.

La session reste récupérable grâce au dernier `LastSeenAtUtc`.

### 10.2 Crash ou reboot

Au prochain démarrage :

- une session persistée comme active est examinée ;
- si le processus principal est toujours présent et cohérent, la session peut continuer ;
- sinon elle est clôturée à `LastSeenAtUtc` ;
- `EndReason = RecoveredAfterUnexpectedShutdown`.

Aucune durée postérieure au dernier timestamp fiable n'est inventée.

## 11. Runtime Sessions

Le runtime Sessions orchestre :

```text
process snapshot
    ↓
signature matching
    ↓
session transition policy
    ↓
persistence
    ↓
current session snapshot
    ↓
UI
```

Le runtime expose un snapshot immutable ou logiquement immutable à l'UI.

Contrat conceptuel :

```csharp
public interface ISessionRuntime
{
    SessionRuntimeSnapshot Current { get; }

    Task InitializeAsync(CancellationToken cancellationToken);

    Task<SessionRuntimeSnapshot> RefreshAsync(
        CancellationToken cancellationToken);

    Task CorrectSessionAsync(
        SessionCorrectionRequest correction,
        CancellationToken cancellationToken);
}
```

Le monitor background et l'UI utilisent le même runtime, sans dupliquer les règles métier.

## 12. Systray et cycle de vie

0.3 introduit un vrai comportement systray.

### Règles

- fermer la fenêtre principale ne signifie pas nécessairement quitter PlayStead ;
- PlayStead peut rester actif dans le systray ;
- le monitoring Sessions continue ;
- l'utilisateur peut restaurer la fenêtre depuis l'icône tray ;
- l'utilisateur doit disposer d'une action explicite **Quitter PlayStead** ;
- une fermeture explicite complète arrête proprement le Generic Host.

Le comportement single-instance 0.1 reste valide :

- une seconde invocation réactive l'instance existante ;
- si la fenêtre est cachée dans le tray, elle est restaurée puis activée.

## 13. UX/UI 0.3

0.3 construit une **vraie structure UX Sessions**, pas un écran de diagnostic jetable.

Elle reste visuellement compatible avec l'interface existante, sans tenter la refonte globale 0.4.

### 13.1 Navigation

Ajouter une entrée principale :

```text
Accueil
Bibliothèque
Sessions
```

### 13.2 Page Sessions

Structure recommandée :

```text
Sessions
────────────────────────────────────────

[ KPI / résumé léger ]

[ Sessions en cours ]
  Jeu
  Depuis
  Durée live
  Statut

[ Historique récent ]
  Jeu
  Date
  Heure début
  Heure fin
  Durée
  Raison
  Badge correction/recovery

[ Détail / action ]
  Voir détails
  Corriger
```

### 13.3 Session active

Une session active affiche :

- nom du jeu ;
- heure de début ;
- durée live ;
- badge `En cours`.

La durée live est calculée en UI à partir du timestamp, sans écrire en DB chaque seconde.

### 13.4 Historique

L'historique affiche au minimum les sessions récentes, triées par date décroissante.

Les badges possibles incluent :

```text
Normal
Récupérée
Corrigée
```

### 13.5 Détail de session

Le détail affiche :

- jeu ;
- début observé ;
- fin observée ;
- durée observée ;
- début/fin corrigés éventuels ;
- durée effective ;
- raison de fin ;
- indication recovery ;
- indication correction.

### 13.6 Correction

Une action **Corriger la session** permet de modifier :

- heure de début ;
- heure de fin ;
- raison facultative.

La validation interdit :

- fin avant début ;
- timestamps absurdes ou hors plage supportée ;
- correction d'une session active d'une manière rendant son état incohérent.

### 13.7 Empty states

La page doit gérer proprement :

- aucune session active ;
- aucun historique ;
- moteur non initialisé ;
- erreur de lecture non fatale.

### 13.8 Bibliothèque

Une carte de jeu peut afficher un indicateur léger lorsque le jeu est actuellement suivi :

```text
● En cours
```

Cet indicateur ne doit pas transformer la bibliothèque en dashboard Sessions.

## 15. Erreurs et dégradation

### Processus inaccessible

Si PlayStead ne peut pas lire les métadonnées d'un processus :

- ignorer ce processus pour ce cycle ;
- journaliser au niveau approprié ;
- ne pas faire échouer tout le monitor.

### SQLite indisponible

Une erreur persistante de persistance Sessions doit :

- être journalisée ;
- remonter un état runtime dégradé ;
- ne pas corrompre silencieusement une session.

### Signature invalide

Une signature sans processus principal valide ne peut pas ouvrir une session.

### Processus transitoire

Un processus qui apparaît et disparaît très rapidement ne doit pas forcément créer une session significative.

0.3 doit prévoir un mécanisme anti-faux-positif simple.

Cible recommandée :

```text
confirmation de présence sur 2 snapshots consécutifs
```

Avec polling 2 s, cela donne environ 2 à 4 s de confirmation avant création définitive.

Le timestamp de début enregistré reste le premier timestamp fiable observé, pas le second snapshot.

---

## 16. Performance

Le moteur Sessions ne doit pas transformer PlayStead en scanner agressif.

Objectifs :

- polling 2 s ;
- pas de scan disque complet à chaque cycle ;
- matching principalement en mémoire ;
- écritures DB heartbeat toutes les 5 s maximum par session active ;
- UI live timer sans write DB à la seconde ;
- aucune opération distante dans le monitor Sessions.

Une baseline CPU/RAM doit être enregistrée avec :

- PlayStead idle sans session ;
- une session active ;
- plusieurs sessions actives si possible.

Utiliser une source de processus fake.

- page Sessions ;
- active sessions ;
- historique ;

### Smoke Windows réel

Le gate 0.3 doit comporter un smoke contrôlé avec un exécutable de test local ou un jeu réel disponible.

Le smoke doit démontrer :

1. PlayStead détecte le processus ;
2. une session démarre ;
3. `LastSeenAtUtc` progresse ;
4. la session apparaît dans l'UI ;
5. la fermeture de fenêtre laisse PlayStead en tray ;
6. le suivi continue ;
7. la restauration de fenêtre fonctionne ;
8. la fin du processus clôture la session ;
9. l'historique affiche la session ;
10. aucune donnée utilisateur n'est écrite à côté de l'exécutable.

Si un jeu réel est utilisé, le rapport doit indiquer précisément lequel.

## 18. Migration SQLite

0.3 ajoute une migration de schéma.

La migration doit être :

- additive ;
- idempotente dans le pipeline d'initialisation existant ;
- compatible avec une base 0.2 réelle ;
- testée sur une DB neuve ;
- testée sur une DB migrée depuis le schéma 0.2.

Tables conceptuelles :

```text
process_signatures
process_signature_entries
game_sessions
session_corrections
```

Le numéro exact de version de schéma sera choisi à partir de la version actuellement utilisée par 0.2 et incrémenté d'une unité.

## 19. Observabilité

Logs minimum :

```text
SessionMonitor started/stopped
signature matched
candidate rejected
session started
session heartbeat
session ended
session recovered
session correction applied
process metadata inaccessible
persistence failure
```

Les logs ne doivent pas être spammés toutes les 2 secondes en fonctionnement nominal.

Le heartbeat peut être `Debug` ou supprimé des logs normaux.

---

## 20. Sécurité / confidentialité

Le moteur Sessions reste strictement local.

0.3 ne doit envoyer :

- aucun nom de processus ;
- aucun chemin exécutable ;
- aucun historique de sessions ;
- aucune durée ;

vers un service distant.

Les chemins locaux restent stockés uniquement dans la base PlayStead locale si nécessaires aux signatures.
