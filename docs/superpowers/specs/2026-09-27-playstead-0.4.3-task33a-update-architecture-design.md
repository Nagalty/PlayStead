# Task 33A — PlayStead multi-channel update architecture

## Scope

Introduce the provider-neutral update architecture for GitHub and Microsoft Store distributions. This task defines runtime contracts, distribution-channel injection, strategy composition, and post-Ready checking. It does not download, verify, install, replace, relaunch, or present final update UI.

## Distribution channel

`PlayStead.Core` exposes `DistributionChannel` with `GitHub` and `MicrosoftStore` values. The value comes from build/package metadata, not runtime filesystem heuristics. The UI project receives a generated assembly metadata value from an MSBuild property; the current default remains GitHub and Store packaging can set the property explicitly.

The functional application version remains the existing `ProductVersion.Version` value. Channel identity is separate and never appended to the functional version.

## Common update contract

`PlayStead.Core` exposes a provider-neutral `IAppUpdateService` and immutable state/value types:

- `AppUpdateStatus`: `Unknown`, `Checking`, `UpToDate`, `UpdateAvailable`, `Error`.
- `AppUpdateActionKind`: `None`, `DownloadAndInstall`, `OpenMicrosoftStore`.
- `AppUpdateState`: status, current version, available version, distribution channel, optional release-notes URI, optional action URI/action kind, and an optional error description.

The contract is safe for UI consumption and does not expose provider-specific clients or package replacement operations.

## Strategy implementations

`GitHubAppUpdateService` implements only the preparation boundary for a future public manifest. A strict manifest model/parser is defined for version, release channel, package URL, SHA-256, release notes URL, and published timestamp. No token, secret, download, hash computation, or installation is performed in 33A.

`MicrosoftStoreAppUpdateService` implements the preparation boundary for a future `StoreContext.GetAppAndOptionalStorePackageUpdatesAsync()` integration. It reports the Store action shape (`OpenMicrosoftStore`) when a future Store check identifies an update. The ProductId is supplied through configuration/composition and remains absent when no real ProductId is known. It never exposes GitHub download or replacement behavior.

## Composition and lifecycle

`PlaySteadHost` selects exactly one strategy from the injected `DistributionChannel` and registers it as `IAppUpdateService`. ViewModels do not branch on channel. The service is invoked after the existing Ready transition on a non-blocking background path. No update check is awaited before `Ready`; failures are represented as `Error` state and do not prevent the application from becoming interactive.

Throttling/persistence are deliberately minimal in 33A. No database migration is added. A later task may add last-check or ignored-version persistence once a concrete check policy exists.

## Packaging audit outcome

The current WPF project already defines an executable icon and functional assembly version through the existing project/core conventions. The current worktree does not establish a verified Microsoft Store/MSIX ProductId. Therefore no ProductId is invented and Store composition remains configurable without a hard-coded value.

## Validation boundaries

Tests cover channel metadata for GitHub and Store builds, strategy selection without cross-channel services, common state transitions, strict GitHub manifest parsing contracts, Store action semantics, and post-Ready non-blocking invocation. No WPF launch is required. No production update download or installation is exercised.
