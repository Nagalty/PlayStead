# PlayStead 0.4 — UX cœur / Dark Copper

**Date :** 2026-09-13

**Branche cible :** `feat/0.4-visual-redesign`

**Baseline Git :** `843c089e77e9460e096c27bc9b47f440fbaea9f3`

**Baseline produit :** PlayStead 0.3 CLOSED — 100 % complete

**Baseline de régression :** 349 tests

**Statut :** référence fonctionnelle, UX et visuelle autoritaire de 0.4 ; implémentation non commencée.

## Portée et lecture des exigences

Cette spec formalise la direction validée pour **PlayStead 0.4 — UX cœur / refonte visuelle globale**. Elle ne constitue pas encore un plan d’implémentation.

Les surfaces, interactions, invariants et exclusions formulés comme obligations sont des exigences. Les listes introduites par « possible », « peut », « selon les données disponibles », « par exemple » ou « éventuellement » sont des possibilités conditionnelles : elles n’autorisent ni données fictives ni backend supplémentaire pour les remplir. Une donnée absente doit être traitée par un état adapté, sans annoncer de fonctionnalité future.

La navigation horizontale et la fiche jeu suivent la maquette existante mentionnée dans le cadrage validé. Les références fonctionnelles à préserver sont la [spec Sessions 0.3](2026-09-12-playstead-0.3-sessions-design.md), la [spec de cycle de vie systray](2026-09-13-playstead-0.3-task09-tray-lifecycle-design.md) et la [checklist d’acceptation 0.3](../../PLAYSTEAD_0.3_ACCEPTANCE_CHECKLIST.md).

## Vision

0.4 doit transformer PlayStead en produit visuellement mature et cohérent sans casser les fondations 0.1–0.3.

La refonte ne se limite pas aux couleurs : elle couvre le shell, la navigation, l’Accueil, la Bibliothèque, la fiche jeu, le panneau rapide, la recherche, Sessions et le détail de session.

## Direction artistique validée

**Dark Copper évolué**

Principes :

* fond ardoise / noir bleuté ;
* cuivre comme accent signature ;
* rendu premium, mature et sobre ;
* `Segoe UI Variable` ;
* Fluent Icons ;
* grille d’espacement 8 px ;
* surfaces sombres hiérarchisées ;
* rayons et élévations cohérents ;
* animations courtes principalement entre 120 et 220 ms ;
* aucun effet RGB ;
* aucun glow gaming gratuit ;
* densité maîtrisée ;
* contraste et focus clavier lisibles.

La navigation reste **horizontale en haut**, conformément à la maquette existante.

Aucune sidebar verticale de navigation. Le panneau rapide à droite reste contextuel et ne remplace pas la top bar.

## Shell / navigation

La navigation principale de la top bar est exactement :

`PlayStead | Accueil | Bibliothèque | Recherche | À signaler | Paramètres`

Les actions de fenêtre complètent cette barre sans constituer des destinations principales.

Sessions reste entièrement accessible via une surface secondaire/contextuelle cohérente avec l’UX existante, sans onglet principal permanent équivalent à Accueil/Bibliothèque et sans suppression de contrat 0.3.

État actif clair avec accent cuivre.

Transitions légères uniquement.

### Retour et restauration du contexte

Au retour d’une fiche jeu ouverte depuis la Bibliothèque, restaurer autant que possible la sous-vue, le mode grille/liste, les filtres, le tri, la position de scroll et la sélection ou le contexte pertinent.

Prendre en charge `Alt+←` et le bouton Retour de la souris. La navigation retour et la restauration doivent être testables.

## Accueil

Créer une vraie vue Accueil en 0.4.

Elle doit utiliser uniquement des données déjà disponibles dans PlayStead.

Contenu possible :

* hero PlayStead compact ;
* état/session active ;
* activité récente ;
* derniers jeux/sessions lorsque les données existantes le permettent ;
* KPI simples ;
* raccourcis Bibliothèque / Sessions.

Pas de nouveau backend uniquement pour l’Accueil.

Pas de dashboard analytique lourd.

Objectif UX :
répondre rapidement à « qu’est-ce qui se passe actuellement dans mon environnement de jeu ? ».

## Bibliothèque

Vue principale par défaut :
**grille premium de jaquettes virtualisée**.

Préserver les performances des grandes bibliothèques : éviter les chargements massifs inutiles et libérer les médias / ressources hors viewport lorsque pertinent.

N’exposer que les filtres et tris dont les métadonnées existent réellement. Aucun filtre fictif.

Chaque jeu peut afficher selon les données disponibles :

* visuel / jaquette ;
* titre ;
* provider ;
* état ;
* badge discret si session active ;
* hover/focus ;
* accès au panneau rapide, puis à la fiche jeu via `Voir la fiche`.

Fallback visuel propre lorsque l’image est absente.

Vue secondaire optionnelle :
**liste compacte**.

Prévoir un toggle grille/liste.

Le choix grille/liste, le tri et les filtres sont persistés localement.

La Bibliothèque reste une bibliothèque :
ne pas la transformer en dashboard Sessions.

### Preview média optionnelle

Une preview vidéo/média n’est pas une exigence MVP et dépend de sources réelles et fiables. Si elle est proposée : délai hover cible d’environ `350–500 ms`, lecture muette, une seule preview active à la fois et arrêt immédiat dès que la carte perd le focus/hover.

## Fiche jeu

Créer une vraie fiche jeu 0.4 basée sur la maquette existante.

Elle peut contenir uniquement les informations déjà réellement disponibles :

* identité du jeu ;
* provider ;
* installation connue ;
* temps local/provider si disponible ;
* dernière activité/session ;
* session active ;
* actions déjà supportées.

### Règle impérative de roadmap

Ne jamais afficher de faux placeholders pour l’environnement local avancé, les mods, le contexte avancé, la communauté ou les données prévues en 0.5–0.8.

La fiche 0.4 n’affiche que les sections dont les données fonctionnent réellement. Les futures sections n’apparaissent que lorsque leur backend existe réellement. Les maquettes 1.0 peuvent les montrer comme vision cible, sans les simuler en 0.4.

La fiche jeu s’enrichira progressivement avec les versions futures.

## Panneau rapide

Ajouter un panneau contextuel latéral à droite depuis la Bibliothèque.

Il reste compact et ne duplique pas la fiche jeu.

Données/actions possibles :

* titre ;
* provider ;
* état ;
* installation ;
* dernière activité ;
* session active ;
* actions déjà existantes ;
* bouton `Voir la fiche` vers la fiche jeu complète.

Interaction :

* clic principal sur la jaquette / carte jeu → ouverture du panneau rapide à droite ;
* `Voir la fiche` depuis le panneau → fiche jeu complète ;
* autres actions secondaires uniquement si réellement supportées.

Le panneau est non bloquant et conserve le contexte Bibliothèque à l’ouverture comme à la fermeture.

## Recherche globale

Recherche intégrée dans la top bar, accessible par `Ctrl+K`.

Scope 0.4 :
**bibliothèque locale PlayStead uniquement**.

Fonctionnement :

* saisie progressive ;
* résultats instantanés ;
* recherche sur toutes les métadonnées locales déjà connues, fiables et pertinentes, sans limitation conceptuelle au titre/provider ;
* navigation clavier ;
* Entrée/clic ouvre le résultat vers sa fiche jeu ;
* Échap ferme la recherche.

Pas de recherche Steam distante.
Pas de recherche Internet.
Pas de catalogue web.
Pas de recherche communautaire.
Pas de backend supplémentaire uniquement pour alimenter la recherche 0.4.

## Bouton Jouer

Le scope 0.4 inclut un **split-button Jouer** minimal :

* clic principal → lancer l’installation préférée ;
* flèche secondaire → choisir ponctuellement une autre installation connue ;
* une seule installation connue → lancement direct ;
* Steam utilise sa chaîne officielle de lancement lorsque applicable.

Ce comportement borné aux installations connues se distingue de la future extension de routage multi-provider complet. Il n’autorise pas un moteur universel de lancement en 0.4.

## À signaler

La surface dédiée `À signaler`, accessible depuis la top bar, présente uniquement les éléments nécessitant réellement une décision, une vérification ou une intervention utilisateur.

Selon les données réellement disponibles, cela peut couvrir une incohérence, une installation ambiguë, un élément nécessitant confirmation ou un problème local identifiable.

Ne pas y placer les notifications de succès ordinaires ni mélanger les erreurs techniques générales avec les décisions utilisateur. La surface reste cohérente avec l’UX de la top bar.

## Persistance d’état UI

Persister localement les préférences et états UX pertinents :

* vue grille/liste ;
* tri et filtres ;
* navigation/restauration lorsque pertinent ;
* position et état de fenêtre selon les mécanismes existants ;
* préférences d’animations, dont `Réduire les animations` ;
* autres préférences purement UI utiles, si nécessaires.

Utiliser la persistance locale PlayStead existante ou une extension bornée de celle-ci. Aucun système cloud.

## Sessions

Conserver intégralement le contrat fonctionnel 0.3.

La refonte Sessions est principalement visuelle/UX, sur une surface secondaire/contextuelle. Ne pas refaire le moteur, modifier les règles de détection ou heartbeat/recovery, ni affaiblir observed/corrected/effective.

Refonte visuelle :

### Session active

Zone prioritaire en haut lorsqu’un jeu tourne :

* jeu ;
* état ;
* heure de début ;
* durée ;
* provider/contexte disponible.

### Historique

Liste compacte et scannable.

États visibles via badges sobres :

* Observed ;
* Corrected ;
* Recovered.

Clic → détail session.

Pas d’analytics avancées ni gros graphiques en 0.4.

## Détail de session

Moderniser `SessionDetailView`.

La hiérarchie doit rendre immédiatement compréhensible :

* données observées ;
* données effectives ;
* correction éventuelle ;
* provenance ;
* état.

Le formulaire de correction conserve son comportement actuel.

La traçabilité reste obligatoire.

## Design system

Réutiliser/restyler en priorité les composants 0.3 :

* `SectionHeader`
* `StatusBadge`
* `KpiCard`
* `EmptyState`

Ajouter uniquement les primitives nécessaires, par exemple :

* top navigation ;
* game card ;
* search box/results ;
* panel standard ;
* icon button ;
* éventuellement `DataListRow` uniquement si plusieurs écrans en ont réellement besoin.

Ne pas créer de framework UI maison inutile.

Éviter la duplication de styles XAML.

## États UI

Prévoir explicitement selon les surfaces :

* loading ;
* empty ;
* unavailable ;
* error ;
* success/confirmation ;
* image absente ;
* provider indisponible.

Le fonctionnement cache-first et hors réseau des versions précédentes doit être conservé.

### Chargement progressif et feedback

Afficher immédiatement les données locales disponibles, puis enrichir progressivement sans attente réseau globale. Aucune donnée secondaire ne justifie un gros spinner plein écran.

Confiner les erreurs à l’élément ou à la section concernée ; l’interface principale reste utilisable si une source secondaire échoue. Présenter des erreurs actionnables lorsque possible et des notifications internes discrètes pour les confirmations/succès, distinctes de `À signaler`.

## Animations

Animations autorisées :

* transition de page ;
* panneau rapide ;
* hover/focus ;
* recherche/menu ;
* apparition discrète ;
* changement d’état live.

Durées principalement :
`120–220 ms`

Pas d’animation permanente gratuite.

La préférence utilisateur **Réduire les animations** supprime ou raccourcit les transitions décoratives et conserve le feedback nécessaire à la compréhension. Navigation, focus et changements d’état, notamment live, restent corrects.

## Accessibilité

Intégrer dès 0.4 :

* contraste lisible ;
* focus clavier visible ;
* navigation clavier cohérente ;
* accent cuivre jamais utilisé comme seule information ;
* états disabled explicites ;
* zones cliquables raisonnables ;
* tooltips pour icon buttons non évidents.

## Performance

Objectifs qualitatifs :

* top bar et routing immédiatement réactifs ;
* recherche locale instantanée à l’échelle raisonnable de la bibliothèque ;
* scroll Bibliothèque fluide ;
* virtualisation obligatoire des surfaces potentiellement volumineuses ;
* aucun chargement synchrone lourd sur le thread UI ;
* baseline de performance mesurable conservée en fin de 0.4.

Ces objectifs n’introduisent aucun SLA ni seuil chiffré non autorisé.

## Architecture recommandée

Approche :
**UI-first avec MVVM propre**.

La majorité des changements doit rester dans `PlayStead.UI`.

Quand une vue doit composer plusieurs sources existantes, préférer un ViewModel / adapter de présentation plutôt que du code métier dans le code-behind.

Ne modifier `Core`, `Data`, `Platform` ou `Providers` que si un besoin réel et démontré de présentation ou d’intégration des exigences minimales 0.4 (Jouer, persistance locale UI) exige une API supplémentaire bornée. Cela n’autorise ni backend fictif ni routage multi-provider complet.

Aucun refactor transversal opportuniste.
