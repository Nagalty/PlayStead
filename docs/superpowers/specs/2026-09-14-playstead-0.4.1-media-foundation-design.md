# PlayStead 0.4.1 — Media Foundation Design

**Date:** 2026-09-14
**Status:** Approved design — ready for implementation planning
**Target:** PlayStead 0.4.1
**Scope:** Media foundation for Steam-first game artwork with multi-provider-ready architecture

## 1. Purpose

PlayStead 0.4 established a reliable technical and UX foundation, but the product still lacks the visual richness required by the validated interface mockups.

The first 0.4.1 objective is therefore to introduce a real media pipeline that can supply game artwork to the existing Library and then to the Home screen without compromising PlayStead's local-first / cache-first philosophy.

This work is not a decorative afterthought. It is the first vertical slice of the new PlayStead development method: code, runtime behavior, UI integration, visual validation, and product coherence must advance together.

## 2. Product principles

The Media Foundation MUST follow these rules:

- Steam is the primary media source when a reliable Steam AppID is available.
- Media already cached locally is preferred over network access.
- Network access MUST NOT block startup or Library rendering.
- Missing artwork MUST degrade to a designed PlayStead fallback, never to broken UI.
- The UI MUST NOT depend directly on Steam, IGDB, or any concrete provider.
- The architecture MUST allow future media providers without rewriting the UI.
- IGDB support is planned architecturally but MUST NOT embed a Twitch/IGDB client secret in the desktop executable.
- No media source may invent or ambiguously assign artwork to a game.
- A slice is not complete until code, tests, runtime, visuals, and product coherence are all validated.

## 3. Normalized asset types

PlayStead 0.4.1 normalizes exactly four media asset types:

| PlayStead asset | Primary use |
| --- | --- |
| `Cover` | Vertical Library cards |
| `Header` | Horizontal cards, including recently played |
| `Hero` | Home hero and game detail hero |
| `Logo` | Transparent game logo layered over hero artwork |

For Steam, these map conceptually to the official Steam library assets:

- `Cover` → Library Capsule
- `Header` → Library Header
- `Hero` → Library Hero
- `Logo` → Library Logo

No additional asset categories are introduced in 0.4.1.

## 4. Architecture

The UI consumes normalized media and never knows its origin.

```text
PlayStead UI
    |
    v
GameMediaResolver
    |
    +--> MediaCache
    |
    +--> IGameMediaProvider
            |
            +--> SteamMediaProvider   [0.4.1 active]
            |
            +--> IgdbMediaProvider    [future, not active]
```

### 4.1 `GameMediaResolver`

Responsibilities:

- accept a game media identity and requested asset type;
- return the best locally available result immediately when possible;
- coordinate provider resolution when local media is missing;
- never expose provider-specific details to the UI;
- never block UI rendering on a remote request;
- fall back deterministically when no reliable asset is available.

### 4.2 `IGameMediaProvider`

A provider abstraction must allow additional media sources later without changing Library or Home UI code.

Conceptually:

```text
CanResolve(identity)
ResolveAsync(identity, assetType)
```

The precise C# contract is an implementation-plan concern, but the boundary must remain provider-neutral.

### 4.3 `SteamMediaProvider`

Steam is the only active remote provider in 0.4.1.

Resolution order for a Steam game:

```text
1. PlayStead media cache
2. Steam local media/cache when usable
3. Steam remote asset source
4. PlayStead fallback
```

IGDB is NOT part of the active 0.4.1 Steam resolution chain.

### 4.4 Future `IgdbMediaProvider`

The architecture must leave a clean insertion point for IGDB, primarily for non-Steam games or missing media.

For 0.4.1:

```text
IGDB_READY_ARCHITECTURE=True
IGDB_ENABLED=False
IGDB_SECRET_EMBEDDED=False
```

No Twitch/IGDB client secret may be compiled into, stored in, or shipped with PlayStead.

A future IGDB integration must first define a safe credential strategy, such as a trusted proxy or another approved mechanism.

## 5. Media identity

Media matching must not rely on uncontrolled title search.

The provider-neutral identity should conceptually carry:

```text
GameMediaIdentity
- Provider
- ProviderGameId
- CanonicalTitle
- ExternalIds
```

For Steam:

- `Provider = Steam`
- `ProviderGameId = Steam AppID`
- the AppID is authoritative for Steam media resolution.

Future external IDs may be persisted once a trustworthy mapping is established.

A failed or ambiguous mapping must return no provider media and use the PlayStead fallback instead of selecting a questionable result.

## 6. Local cache

All PlayStead-managed media must live under the user profile:

```text
%LOCALAPPDATA%\PlayStead\Media\
```

Initial layout:

```text
Media\
├── steam\
│   └── <AppId>\
│       ├── cover.*
│       ├── header.*
│       ├── hero.*
│       ├── logo.*
│       └── metadata.json
└── fallback\
```

No media file may be stored beside the PlayStead executable.

### 6.1 Cache metadata

`metadata.json` may record, when known:

```text
Source
ExternalId
AssetType
RetrievedAtUtc
SourceUri
ETag
LastModified
Width
Height
```

Not every field is mandatory. The cache must tolerate incomplete metadata.

### 6.2 Cache behavior

The cache must support:

- deterministic lookup;
- atomic replacement of successfully downloaded assets;
- reuse across application restarts;
- no repeated download when a valid local asset already exists;
- preservation of the last valid asset when refresh fails.

Cache expiry and refresh policy should remain conservative in 0.4.1. The initial implementation does not require an aggressive invalidation system.

## 7. Runtime and network behavior

Network access is never on the critical path for application startup or Library display.

Expected flow:

```text
request asset
    |
    +--> cached asset exists
    |       -> display immediately
    |
    +--> cached asset absent
            -> display PlayStead fallback immediately
            -> resolve asynchronously
            -> cache successful result
            -> notify UI
            -> replace fallback with artwork
```

Failure behavior:

- offline → fallback/local cache remains usable;
- timeout → fallback/local cache remains usable;
- invalid image → discard invalid response and keep fallback/local valid media;
- provider error → no crash and no blocking modal;
- stale but valid cached media → keep displaying the cached asset.

## 8. PlayStead fallback artwork

The current raw empty rectangle / generic diamond is not considered a finished fallback.

0.4.1 must introduce a real PlayStead artwork fallback with:

- Dark Copper visual language;
- readable game title;
- discrete provider label when useful;
- deterministic presentation;
- no false artwork;
- no fake screenshot;
- no dependency on network access.

The fallback must be good enough to remain in the final UI for unsupported games.

## 9. Vertical-slice implementation strategy

The Media Foundation is deliberately implemented in small visible slices.

### Slice 1 — First real Library Cover

Scope:

- minimal `MediaCache`;
- minimal `GameMediaResolver`;
- minimal `SteamMediaProvider`;
- one real Steam `Cover`;
- one real Library card wired to the pipeline;
- PlayStead fallback.

Exit criteria:

```text
CODE_GREEN=True
TESTS_GREEN=True
RUNTIME_GREEN=True
VISUAL_GREEN=True
PRODUCT_COHERENCE_GREEN=True
```

The slice is not closed until a real artwork is visible in the running PlayStead application and visually accepted.

### Slice 2 — Full Library Covers

Scope:

- apply the same cover pipeline to all compatible Steam Library items;
- preserve virtualization/responsiveness;
- cache successful assets;
- show the finished fallback for unresolved games;
- validate Grid and List behavior.

### Slice 3 — Header / Hero / Logo

Scope:

- extend the same provider/cache/resolver system;
- no parallel media architecture;
- validate all three asset types independently.

### Slice 4 — Home integration

Scope:

- begin rebuilding the validated PlayStead Home mockup;
- use real media from the Media Foundation;
- retain real-data-only product behavior;
- no fake KPI or fake editorial content.

Home implementation is a separate UI vertical slice that consumes the completed media foundation.

## 10. Testing strategy

Strict RED → GREEN remains mandatory.

Tests should cover behavior, not implementation trivia.

Minimum areas:

### Core / resolver behavior

- cached asset wins over provider access;
- missing cache triggers provider resolution;
- failed provider resolution returns fallback behavior;
- unsupported identity does not guess;
- provider-specific details do not leak into UI-facing results.

### Cache

- deterministic paths;
- user-profile-only storage;
- successful asset persistence;
- failed refresh preserves last valid media;
- invalid/corrupt asset is rejected safely.

### Steam provider

- exact Steam AppID identity;
- expected asset request construction;
- no title-based guessing;
- unsupported/missing AppID is rejected cleanly.

### UI contract

- Library card can display fallback immediately;
- Library card updates when resolved media becomes available;
- Grid/List remain functional;
- no startup blocking on media resolution.

### Runtime / visual

Automated tests are necessary but insufficient.

Every slice requires:

- launch the real application;
- inspect the real Library/Home surface;
- validate asset crop, aspect ratio, readability, fallback, loading transition, and layout;
- correct code/UI mismatches before closing the slice.

## 11. Performance constraints

No artificial SLA is introduced.

The implementation must preserve these product-level constraints:

- no blocking remote media request during startup;
- no unbounded parallel downloads;
- no UI-thread image decoding/download work that causes visible stalls;
- Library virtualization must remain effective;
- repeated navigation must reuse cached media;
- media loading must not cause uncontrolled memory growth.

A fresh performance baseline should be captured after the full Library cover rollout.

## 12. Error handling and observability

Media failures are non-fatal.

Logging should distinguish:

- cache hit;
- cache miss;
- local Steam asset hit;
- remote Steam success;
- remote Steam failure;
- invalid image;
- fallback used.

Logs must not spam normal users with repeated identical failures.

No modal error is shown solely because artwork failed to resolve.

## 13. Security and privacy

- no IGDB/Twitch client secret embedded in PlayStead;
- no Steam credentials required;
- no account password or Steam Web API key required for media resolution;
- no arbitrary executable content downloaded;
- only expected image content is accepted into the media cache;
- user media remains under `%LOCALAPPDATA%\PlayStead`.

## 14. Out of scope for 0.4.1 Media Foundation

The following are explicitly excluded:

- active IGDB integration;
- Epic Games media provider;
- GOG media provider;
- SteamGridDB integration;
- manual artwork editor;
- manual artwork download workflow;
- community artwork selection;
- artwork upload;
- dozens of media variants;
- blocking preload of the entire Library;
- fake metadata or fake media;
- unrelated refactors.

## 15. Definition of Done

The Media Foundation is not considered complete only because unit tests pass.

For every vertical slice:

```text
CODE_GREEN=True
TESTS_GREEN=True
RUNTIME_GREEN=True
VISUAL_GREEN=True
PRODUCT_COHERENCE_GREEN=True
```

For the complete 0.4.1 Media Foundation:

- all intended Steam Library covers resolve through the new pipeline when available;
- unresolved games have a finished PlayStead fallback;
- cache-first behavior is proven;
- offline behavior is proven;
- the real Library visually demonstrates the system;
- no UI dependency on Steam-specific media APIs exists;
- IGDB remains disabled and no secret is embedded;
- Release build is 0 warnings / 0 errors;
- full automated suite is GREEN;
- runtime smoke is GREEN;
- visual acceptance is GREEN;
- final worktree is clean after the accepted commit.

## 16. Development-process rule going forward

PlayStead development now uses vertical slices as the default method.

A substantial feature must evolve together with its UI whenever it has a user-visible consequence.

A milestone cannot be declared 100% based solely on implementation and automated tests. Runtime and visual/product acceptance are first-class gates.
