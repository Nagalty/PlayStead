# PlayStead 0.2 — Steam Reference Design

**Date:** 2026-09-12
**Status:** Proposed for approval
**Target version:** `0.2.0-dev`
**Baseline:** PlayStead `0.1.0-dev`, foundation complete
**Branch baseline:** `feat/0.1-local-foundation`
**Validated baseline HEAD:** `b644178d0d0eeb4c32f95f74eae17dcb5d08ab90`

---

## 1. Goal

PlayStead 0.2 turns the current Steam local-library support into a reliable Steam reference engine able to answer, conservatively and explainably:

- what Steam game is installed locally;
- which Steam branch is installed;
- which depot manifests are installed;
- what the latest known remote state is for that same branch;
- whether the local installation is current;
- whether an update is available;
- whether a newer Steam-side build exists without enough evidence to claim an installable update;
- when the evidence is insufficient and the state must remain unknown.

The 0.2 scope is **not** an interface redesign. The existing 0.1 library UI is extended only enough to expose and validate the new Steam state.

---

## 2. Product principles

### 2.1 Conservative truth over optimistic inference

PlayStead must never claim an update solely because a remote `BuildID` differs from the local one.

The preferred evidence order is:

1. exact branch identity;
2. relevant depot manifest identities for that branch;
3. local versus remote depot comparison;
4. `BuildID` as a secondary signal only;
5. explicit unknown state when evidence is incomplete or contradictory.

When evidence is insufficient, **Unknown wins**.

### 2.2 Local-first

Local Steam evidence is authoritative for what is actually installed.

Remote Steam evidence is enrichment used to determine whether the installed content is current.

Remote failure must never make the local library disappear or block PlayStead startup.

### 2.3 Cache-first

PlayStead starts from persisted state immediately.

Remote evidence is considered fresh for **6 hours**.

If cached remote evidence is older than 6 hours, PlayStead:

1. shows the cached state immediately;
2. marks refresh as in progress where appropriate;
3. starts a non-blocking remote refresh;
4. updates the state when fresh evidence arrives.

A manual global refresh bypasses TTL.

### 2.4 No Steam credentials

The 0.2 remote provider uses **SteamCMD anonymous access**.

PlayStead must not require or persist:

- Steam account credentials;
- Steam password;
- Steam Guard secrets;
- Steam Web API key.

## 3. Scope

### Included

- Steam local branch detection.
- Steam local depot manifest detection.
- Anonymous SteamCMD remote metadata retrieval.
- Remote branch/depot evidence parsing.
- Persistent remote evidence cache.
- 6-hour TTL.

- Single remote refresh campaign at a time.

### Explicitly excluded

- UX/navigation redesign.

- Search/filter overhaul.

- Launch management.
- Patch notes/news aggregation.
- Automatic background scheduler independent of PlayStead runtime.
- Public release packaging work beyond normal dev validation.

These belong to later `0.x` phases.

## 4. User-visible update states

The Steam update engine exposes exactly five top-level states.

### `UpToDate`

Display label: **À jour**

Meaning:

- branch is known;
- relevant local depot manifests are known;
- relevant remote depot manifests for the same branch are known;
- all required remote depot manifests match the installed manifests.

### `UpdateAvailable`

Display label: **Mise à jour disponible**

Meaning:

- branch is known;
- local and remote depot evidence is sufficient;
- at least one required remote depot manifest differs from the installed manifest.

This is the only state that positively claims that the installed Steam content is behind.

### `NewVersionDetected`

Display label: **Nouvelle version détectée**

Meaning:

- a meaningful remote version/build signal differs;
- but depot evidence is insufficient to prove that the currently installed content requires an update.

Typical example:

- remote `BuildID` changed;
- relevant depot manifests are unchanged or unavailable.

This state is informational, not equivalent to `UpdateAvailable`.

### `Unknown`

Display label: **État inconnu**

Meaning:

- branch cannot be identified reliably;
- remote branch does not exist or cannot be queried;
- required depot evidence is missing;
- parsing failed;
- evidence is contradictory;
- SteamCMD failed and there is no usable prior remote evidence.

An explicit reason accompanies this state.

### `Checking`

Display label: **Vérification en cours**

Meaning:

- a remote refresh is actively running;
- the UI may continue showing the previous persisted result alongside the transient checking indicator.

`Checking` is transient runtime state, not a replacement for cached evidence.

## 5. Evidence model

### 5.1 Local Steam evidence

Create a dedicated immutable model representing what is installed.

Suggested shape:

```csharp
public sealed record SteamLocalEvidence(
    string AppId,
    string? BuildId,
    string? BranchName,
    IReadOnlyDictionary<string, string> DepotManifestIds,
    DateTimeOffset ObservedAtUtc);
```

Rules:

- `AppId` is required.
- `BranchName` is normalized.
- `public` is only used when local evidence explicitly establishes it or Steam semantics make it unambiguous from the local manifest.
- A missing/ambiguous branch is represented as unknown, never silently coerced to `public`.
- Depot key = depot ID.
- Depot value = installed manifest ID.

### 5.2 Remote Steam evidence

```csharp
public sealed record SteamRemoteEvidence(
    string AppId,
    string BranchName,
    string? BuildId,
    IReadOnlyDictionary<string, string> DepotManifestIds,
    DateTimeOffset ObservedAtUtc,
    SteamRemoteEvidenceSource Source);
```

`Source` for 0.2:

```csharp
public enum SteamRemoteEvidenceSource
{
    SteamCmdAnonymous
}
```

Remote evidence is always branch-specific.

### 5.3 Evaluation result

```csharp
public sealed record SteamUpdateEvaluation(
    SteamUpdateState State,
    SteamUpdateReason Reason,
    DateTimeOffset EvaluatedAtUtc,
    IReadOnlyList<string> ChangedDepotIds);
```

`SteamUpdateReason` is a stable machine-readable enum. The UI maps it to short localized text.

Examples:

- `DepotManifestsMatch`
- `DepotManifestMismatch`
- `RemoteBuildChangedWithoutDepotDifference`
- `LocalBranchUnknown`
- `RemoteBranchUnavailable`
- `LocalDepotEvidenceMissing`
- `RemoteDepotEvidenceMissing`
- `RemoteRefreshFailedWithoutCache`
- `EvidenceContradictory`

The evaluator must not emit human UI strings.

## 6. Branch rules

Branch handling is strict.

### Rules

- Compare local evidence only against the **same remote branch**.
- Branch names are compared using a documented normalization rule.
- Never silently fall back from an unknown/beta branch to `public`.
- If the local branch is unknown, evaluation is `Unknown`.
- If the local branch is known but absent remotely, evaluation is `Unknown`.
- Password-protected/private beta branches that cannot be inspected anonymously are `Unknown`, not `UpToDate`.
- `public` is not treated as a magic fallback.

This avoids false positives for users deliberately running beta or experimental branches.

---

## 7. Depot comparison rules

Depot manifests are the primary update evidence.

The evaluator receives already-normalized local and remote evidence and performs no I/O.

### Required behavior

If branch identity is unknown:

```text
Unknown
```

If local required depot evidence is missing:

```text
Unknown
```

If remote required depot evidence is missing:

```text
Unknown
```

If every comparable required depot manifest matches:

```text
UpToDate
```

If one or more required depot manifests differ:

```text
UpdateAvailable
```

If depot manifests match but remote `BuildID` differs:

```text
NewVersionDetected
```

If `BuildID` differs but depot evidence is incomplete:

```text
NewVersionDetected
```

only when the available evidence is coherent enough to establish that a remote version signal genuinely changed. Otherwise:

```text
Unknown
```

The evaluator must return the IDs of depots that differ when `UpdateAvailable` is emitted.

## 8. SteamCMD integration

### 8.1 Boundary

SteamCMD is isolated behind a provider interface.

Suggested contract:

```csharp
public interface ISteamRemoteEvidenceSource
{
    Task<SteamRemoteEvidenceResult> QueryAsync(
        string appId,
        string branchName,
        CancellationToken cancellationToken);
}
```

The rest of PlayStead must not know how SteamCMD is invoked.

### 8.2 Process execution

Create a dedicated process runner abstraction:

```csharp
public interface ISteamCmdRunner
{
    Task<SteamCmdRunResult> RunAsync(
        SteamCmdRequest request,
        CancellationToken cancellationToken);
}
```

Responsibilities:

- locate configured/bundled SteamCMD executable;
- build anonymous command arguments;
- redirect stdout/stderr;
- enforce timeout;
- kill the child process tree on timeout/cancellation;
- capture exit code;
- return raw output;
- never parse update semantics.

### 8.3 Timeout

Use one bounded timeout per app query/campaign step.

Timeout is a technical failure, not evidence that the game is current or outdated.

### 8.4 Parsing

SteamCMD output parsing belongs in a separate parser component.

Suggested boundary:

```csharp
public interface ISteamCmdAppInfoParser
{
    SteamRemoteEvidenceParseResult Parse(
        string appId,
        string branchName,
        string rawOutput);
}
```

The parser:

- extracts branch-specific build metadata;
- extracts branch-specific depot manifest IDs;
- does not access disk/network;
- is exhaustively fixture-tested.

### 8.5 SteamCMD availability

0.2 must distinguish:

- SteamCMD available and query succeeds;
- SteamCMD missing;
- SteamCMD process fails;
- timeout;
- output malformed;
- requested branch unavailable.

No one of these may crash application startup.

## 9. Remote cache

Remote evidence is persisted separately from local installation data.

### Recommended persistence

SQLite table dedicated to Steam remote evidence.

Logical schema:

```text
steam_remote_evidence
- app_id
- branch_name
- build_id
- depot_manifests_json
- observed_at_utc
- source
- schema_version
```

Primary identity:

```text
(app_id, branch_name)
```

### Rules

- TTL: **6 hours**.
- Store successful evidence only.
- Do not overwrite a valid cached record with malformed/failed query data.
- Failed refresh updates runtime diagnostics but preserves last good evidence.
- Cache age is based on `ObservedAtUtc`.
- Remote cache can be invalidated per app/branch or globally.
- Manual global refresh ignores TTL but still preserves last good evidence on failure.

---

## 10. Refresh orchestration

Create a provider-level coordinator, not UI logic.

Suggested conceptual component:

```text
SteamRemoteRefreshCoordinator
```

Responsibilities:

- decide whether cache is fresh;
- schedule stale app/branch queries;
- enforce one refresh campaign at a time;
- expose progress/events;
- persist successful remote evidence;
- re-evaluate update state after evidence changes;
- honor cancellation at application shutdown.

### Concurrency

Only one global Steam remote campaign may run at a time.

Repeated refresh requests while one is active must either:

- join the active campaign; or
- return an explicit already-running result.

They must never launch overlapping SteamCMD storms.

### Startup

Startup behavior:

1. load local library/cache;
2. display current library immediately;
3. load cached remote evidence;
4. evaluate current known state;
5. if remote cache is stale, start refresh asynchronously;
6. update presentation as fresh results arrive.

Application startup must not await the full remote Steam campaign.

---

## 11. Failure and fallback behavior

### Remote failure with valid cached evidence

Keep the prior evaluation based on the last successful evidence.

Expose:

- last successful remote verification time;
- remote refresh failure diagnostic.

Do not downgrade to `Unknown` solely because the newest refresh failed.

### Remote failure without cached evidence

State:

```text
Unknown
```

Reason:

```text
RemoteRefreshFailedWithoutCache
```

### Local parsing failure

Do not reuse stale local branch/depot evidence as though it described the current installation unless explicitly marked as cached historical evidence.

Current local truth and remote cached truth remain separate concepts.

0.2 does not redesign PlayStead.

Suggested minimal additions:

## 14. Structured events and diagnostics

0.2 introduces stable diagnostics around remote refresh.

Useful events:

```text
SteamRemoteRefreshStarted
SteamRemoteAppQueryStarted
SteamRemoteAppQuerySucceeded
SteamRemoteAppQueryFailed
SteamRemoteRefreshCompleted
SteamUpdateStateChanged
SteamRemoteRefreshSkippedFreshCache
SteamRemoteRefreshRequestCoalesced
```

Each event should contain relevant structured fields such as:

- app ID;
- branch;
- duration;
- result category;
- cache age;
- previous/new update state;
- failure category.

Do not log secrets because 0.2 has no Steam credentials.

Raw SteamCMD output should not be emitted wholesale at normal log level.

## 15. Components and boundaries

### `PlayStead.Core`

Owns:

- `SteamUpdateState`;
- `SteamUpdateReason`;
- evaluation result types if provider-neutral placement is not preferable;
- pure comparison policy.

No process execution.
No SQLite.
No WPF.

### `PlayStead.Providers`

Owns:

- Steam local evidence extraction;
- SteamCMD request/result models;
- SteamCMD runner;
- SteamCMD parser;
- remote evidence source;
- refresh orchestration policy where Steam-specific.

### `PlayStead.Data`

Owns:

- migration for remote evidence cache;
- repository/store for Steam remote evidence;
- serialization of depot manifests;
- transaction behavior.

### `PlayStead.UI`

Owns:

- wiring into startup/runtime;
- minimal status presentation;
- manual refresh command;
- localized labels/reasons.

### `PlayStead.Platform`

Owns only generic process/platform utilities if they become genuinely reusable.

Do not move Steam-specific process semantics into `Platform` merely because SteamCMD is an executable.

## 17. Test strategy

0.2 remains strict TDD RED → GREEN.

### Pure evaluator tests

Cover at minimum:

- same branch + all depots equal => `UpToDate`;
- same branch + one depot mismatch => `UpdateAvailable`;
- several depot mismatches => all changed depot IDs returned;
- local branch unknown => `Unknown`;
- remote branch unavailable => `Unknown`;
- local depots missing => `Unknown`;
- remote depots missing => `Unknown`;
- build differs + depots equal => `NewVersionDetected`;
- build differs + insufficient coherent evidence => `Unknown` or `NewVersionDetected` according to explicit policy fixture;
- branch mismatch never compares against public;
- evaluator deterministic and side-effect free.

### Steam local evidence tests

Fixtures for:

- public branch;
- beta branch;
- missing branch field;
- multiple depots;
- missing depot manifest;
- malformed manifest;
- known local BuildID.

### SteamCMD parser tests

Recorded fixture files only.

Cover:

- public branch;
- named beta;
- multiple depots;
- build metadata;
- branch absent;
- malformed output;
- partial output;
- changed build with unchanged depots.

No live Steam network dependency in unit tests.

### Cache/store tests

Cover:

- insert;
- replace same app/branch;
- preserve other branch;
- deserialize depot dictionary;
- TTL boundary exactly 6h;
- failed refresh does not destroy last good cache;
- schema migration rollback/backup conventions consistent with 0.1.

### Coordinator tests

Cover:

- fresh cache => no remote query;
- stale cache => remote query;
- manual refresh => query despite fresh cache;
- one campaign at a time;
- concurrent refresh request coalescing;
- success persists evidence;
- failure preserves cached evidence;
- cancellation;
- non-blocking startup integration.

### UI tests

Only minimal contracts:

- correct label for each update state;
- checking state visible;
- last verification exposed;
- global refresh command routed;
- no Steam parsing logic in UI.

## 18. Runtime validation

Real Windows smoke for 0.2 must include at least:

- current real Steam library still detected;
- one normal public-branch game queried remotely;
- cached result survives restart;
- second restart inside 6h does not unnecessarily re-query;
- manual refresh bypasses TTL;
- remote failure preserves last known state;
- PlayStead startup remains non-blocking;
- single-instance behavior from 0.1 remains intact;
- no Steam credentials requested or stored;
- no new user data beside executable.

If a beta-branch game is available on the validation machine, add a real branch smoke. If not, branch behavior remains fully covered by fixtures/tests and is not faked in runtime evidence.

## 19. Migration and compatibility

0.2 adds data but must preserve the 0.1 user profile.

Requirements:

- existing `playstead.db` migrates forward;
- migration follows current backup/rollback safety;
- existing local library data remains readable;
- `window-placement.json` remains untouched;
- failed migration must not silently destroy the 0.1 database;
- no manual user cleanup required for normal upgrade.

---

## 20. Performance expectations

0.2 must preserve the 0.1 startup philosophy.

The 0.1 measured baseline was approximately:

- cold-ish window ready: 507 ms;
- warm average window ready: 452 ms;
- warm working set average: 152.94 MiB;
- publish size: 3.8 MiB.

0.2 does not define a hard SLA from these values.

However:

- remote Steam querying must not be placed on the blocking startup path;
- significant startup regression must be investigated;
- a new performance baseline is recorded at 0.2 completion.

---

## 21. Security and privacy

- no Steam username/password storage;
- no Steam Guard secret;
- no Steam Web API key;
- anonymous SteamCMD only;
- sanitize command-line logging;
- no arbitrary command execution from remote metadata;
- SteamCMD arguments constructed from validated app ID/branch inputs;
- process timeout and cancellation mandatory;
- user data remains under `%LOCALAPPDATA%\PlayStead`.

## 23. Definition of done

PlayStead 0.2 is complete only when all of the following are true:

- local Steam evidence includes branch and depot manifests;
- anonymous SteamCMD remote evidence works behind an interface;
- remote evidence cache is persisted with 6-hour TTL;
- manual global refresh works;
- automatic stale refresh is non-blocking;
- concurrent remote campaigns are prevented/coalesced;
- evaluator uses depot manifests as primary proof;
- BuildID alone never produces `UpdateAvailable`;
- five update states are implemented;
- every `Unknown` result has a machine-readable reason;
- failed refresh preserves last good evidence;
- minimal UI exposes the result without 0.4 redesign;
- automated suite is fully green;
- existing 0.1 behaviors remain green;
- Windows runtime smoke passes;
- performance baseline is recorded;
- documentation and CI are updated;
- working tree is clean at final gate.

## 24. Non-goals reminder

0.2 is the **Steam reference engine**, not the final PlayStead experience.

The success criterion is trustworthy Steam state, not visual completeness.

The full UX/UI evolution remains a later milestone.
