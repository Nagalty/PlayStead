# PlayStead 0.3 Sessions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construire PlayStead `0.3.0-dev` avec suivi local réel des sessions de jeu, signatures de processus persistées, recovery, systray et une vraie UX Sessions déjà structurée avant la refonte globale 0.4.

**Architecture:** Le suivi des sessions reste dans l'unique processus WPF et le Generic Host existant. Le domaine et le matching restent purs dans `PlayStead.Core`, SQLite persiste signatures/sessions/corrections, `PlayStead.Platform` fournit les snapshots processus Windows, et `PlayStead.UI` orchestre monitoring, systray et présentation.

**Tech Stack:** C# 14 / .NET 10, WPF, SQLite, Microsoft Generic Host / DI, xUnit, PowerShell 7, GitHub Actions Windows.

**Spec:** `docs/superpowers/specs/2026-09-12-playstead-0.3-sessions-design.md`

## Global Constraints

- Baseline obligatoire : `61996c2430511f072b9489e03c83d4b7253d769c`.
- Branche : `feat/0.3-sessions`.
- Version : `0.3.0-dev`.
- Windows 10/11 uniquement.
- Aucun agent, daemon ou service Windows séparé.
- Le processus principal réel est la source de vérité d'une session.
- Un auxiliaire, launcher, serveur dédié, crash reporter ou outil ne peut pas ouvrir seul une session.
- Polling cible : 2 secondes.
- Confirmation anti-faux-positif : 2 snapshots consécutifs.
- Heartbeat persistant : 5 secondes.
- Plusieurs sessions actives simultanément doivent être supportées.
- Aucune reconstruction rétroactive d'une session jamais observée.
- Temps provider et temps observé PlayStead restent séparés.
- Une correction manuelle ne détruit jamais les timestamps observés.
- La fenêtre peut être cachée en systray pendant que le monitoring continue.
- La page Sessions de 0.3 est fonctionnelle et structurée ; le redesign visuel global reste pour 0.4.
- Aucun graphique, calendrier, objectif, analytics avancé ou cloud en 0.3.
- Aucun test automatisé ne dépend d'un vrai jeu ou du réseau.
- Strict TDD : aucun code production d'une Task avant observation de son RED valide.
- Chaque correction de script/fichier utilise un nouveau nom explicite (`FIX01`, `FIX02`, etc.).
- Chaque Task CLOSED doit annoncer la progression pondérée réelle.

- [ ] **Step 1: Write RED tests for start/heartbeat/end invariants**

Tests must prove:

```text
Start:
- creates Active
- observed start is first reliable observation
- last seen initially equals first reliable observation

Heartbeat:
- preserves SessionId/GameId/start
- advances LastSeenAtUtc
- never moves LastSeenAtUtc backwards

- requires Active input
- ends at last reliable seen time
- preserves observed start
- assigns requested EndReason
```

```csharp
public void End_recovered_session_at_last_reliable_timestamp()

    Assert.Equal(SessionState.Recovered, result.Session!.State);
```
