# PlayStead 0.2 — Steam Reference Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construire le moteur Steam de référence de PlayStead 0.2 : preuves locales branche/depots, preuves distantes via SteamCMD anonyme, cache 6 h, évaluation conservatrice de l’état de mise à jour, refresh non bloquant et affichage UI minimal.

**Architecture:** Les types d’évidence et l’évaluateur pur vivent dans `PlayStead.Core`; `PlayStead.Providers` collecte les preuves Steam locales et distantes; `PlayStead.Data` persiste les preuves locales/distantes; `PlayStead.UI` orchestre le cache-first, le refresh et la présentation minimale. SteamCMD est isolé derrière un runner et un parser testables sans réseau.

**Tech Stack:** C# / .NET 10, WPF, SQLite, Microsoft Generic Host/DI, xUnit, PowerShell 7, GitHub Actions, SteamCMD anonyme.

**Spec:** `docs/superpowers/specs/2026-09-12-playstead-0.2-steam-reference-design.md`

## Global Constraints

- Version de développement cible : `0.2.0-dev`.
- Baseline 0.1 validée : HEAD `b644178d0d0eeb4c32f95f74eae17dcb5d08ab90`.
- Nouvelle branche de travail : `feat/0.2-steam-reference`.
- Windows 10/11 uniquement pour cette phase.
- Steam est le seul provider distant de la 0.2.
- SteamCMD anonyme uniquement : aucun compte, mot de passe, secret Steam Guard ou clé Web API.
- TTL du cache distant : exactement 6 heures.
- Depot manifests = preuve principale.
- `BuildID` seul ne doit jamais produire `UpdateAvailable`.
- Branche exacte ou `Unknown` ; aucun fallback silencieux vers `public`.
- Un seul refresh distant global à la fois ; appels concurrents coalescés.
- Startup WPF non bloquant : aucune campagne SteamCMD attendue sur le chemin critique.
- Échec distant avec cache valide : conserver la dernière preuve réussie.
- Échec distant sans cache : `Unknown`.
- UI 0.2 minimale ; aucune refonte UX 0.4 anticipée.
- TDD strict RED → GREEN pour chaque lot.
- Aucun test unitaire ne dépend du réseau Steam réel.
- Build Release avec 0 warning / 0 erreur.
- Les données utilisateur restent sous `%LOCALAPPDATA%\PlayStead`.
- Ne jamais écraser un script PowerShell de correction : utiliser `_FIX01`, `_FIX02`, etc.

    Assert.Equal(SteamUpdateState.Unknown, result.State);
    Assert.Equal(SteamUpdateReason.LocalBranchUnknown, result.Reason);
}

Also cover:

```text
- several mismatched depots -> sorted changed depot IDs
- remote branch unavailable -> Unknown
- local depots empty -> Unknown
- remote depots entirely absent + changed BuildID -> NewVersionDetected
- remote depots partially missing -> Unknown
- branch mismatch -> Unknown/EvidenceContradictory
- refresh failed without evidence -> Unknown/RemoteRefreshFailedWithoutCache
- evaluator never returns Checking
```

Policy refinement for incomplete depot evidence:

```text
remote depot set entirely empty + trustworthy changed BuildID
    => NewVersionDetected

remote depot set partially contains local installed depots
    => Unknown / RemoteDepotEvidenceMissing
```

This resolves the spec’s “coherent incomplete evidence” case without creating false update positives.

- [ ] **Step 4: Implémenter l’évaluateur minimal**

Rules in implementation order:

```text

10. compare manifest IDs for every local installed depot
11. differences -> UpdateAvailable + changed IDs
12. no depot difference + changed BuildID -> NewVersionDetected
13. otherwise -> UpToDate
```

## Ambiguity resolved

The spec allowed `NewVersionDetected` when depot evidence is incomplete but a trustworthy BuildID changed. The implementation plan makes the rule deterministic:

```text
remote depot set entirely absent + changed BuildID
    => NewVersionDetected

remote depot set partially missing relative to installed local depots
    => Unknown
```

This prevents partial depot data from being interpreted as update proof.

## Architecture guardrails

- `PlayStead.Data` depends only on Core contracts, not Providers.
- SteamCMD implementation stays in Providers.
- UI never parses Steam manifests or SteamCMD output.
- Evaluator performs no I/O.
- Remote network/process dependencies are faked in automated tests.
- Runtime network proof exists only in controlled smoke validation.
